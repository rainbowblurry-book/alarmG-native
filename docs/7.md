## Your Expo/OTA Question — Yes, With One Condition

You **can** push JS-only updates without a new build, using **EAS Update** (`eas update`). The rule is exact: every build carries a `runtimeVersion`, and an update only applies to devices whose installed build has a **matching** runtime version. As long as a change is pure JavaScript/TypeScript logic, styling, or assets — no new native package, no config-plugin change, no permission change — you can `eas update` it straight to your installed build with no rebuild.[^9_1][^9_2][^9_3]

The moment you add a native dependency (like `expo-image-picker`, `expo-document-picker`, or the auto-launch Kotlin module), that requires a new `eas build` first — OTA cannot inject native code into an already-compiled binary. The recommended config for this (per current Expo docs) is:[^9_2][^9_1]

```json
{
  "expo": {
    "runtimeVersion": { "policy": "fingerprint" },
    "updates": { "url": "https://u.expo.dev/<your-project-id>" }
  }
}
```

Run `eas update:configure` once to wire this up if it isn't already — it'll compute the runtime version from your native code automatically, so it only changes when something native actually changes. After that, this next big native build becomes the new baseline, and *future* JS-only tweaks (colors, copy, bug fixes, even the tab-lock/wheel-disable fixes if you push them separately) can ship instantly via `eas update` with no Codespaces build queue wait.[^9_4][^9_5]

## What `eas build:dev` Actually Does

It's a wrapper that combines three things you did manually today into one command:

1. Checks your project's **fingerprint** (a hash of everything that affects native code — dependencies, config plugins, permissions) against your existing builds.
2. If a build with a **matching fingerprint** already exists, it skips rebuilding entirely and just launches Metro pointed at that build — no wasted 10-15 minute build.
3. If no matching build exists, it kicks off a new one automatically (same as `eas build`), then starts Metro once it's ready.

This directly solves the problem you hit today: you had to manually run `eas build:list`, read through five builds, compare commit hashes and profiles by eye, and figure out which one was stale. `eas build:dev` does that comparison for you via the fingerprint instead of you eyeballing commits.

## Use It Tomorrow

Once your new development build finishes and is installed on your phone, just run:

```bash
eas build:dev
```

It'll detect that your current code's fingerprint matches the build you just made, skip rebuilding, and start Metro directly — no more `--dev-client` flag juggling, no more `EXPO_PACKAGER_PROXY_URL` guesswork (it typically handles the port-forwarding prompt for you in Codespaces).

## One Caveat for Your Setup

`eas build:dev` can auto-install a build onto a device only when it's connected via **USB with `adb`** or is a simulator/emulator. Since your Samsung connects over network (Codespaces has no USB link to your phone), it can't push the APK to your phone automatically — you'll still need to manually download and sideload the APK **once** after each new build, exactly like you did today.
