## 1. What the app is
An Android-only alarm clock. When it rings you can't simply dismiss it:
1. **Movement mission.** Walk or shake until the accelerometer counts N movements (default 15).
2. **Barcode mission.** Scan the barcode of a real household item you registered in Setup.
3. **Snooze** only with your own 10-digit PIN. Optional "cruelty mode" halves every next snooze (floor 20 s).

There is one alarm with repeat days (Sun=0 … Sat=6).

## 4. Alarm flow today (verified)
1. **Arm** (`AlarmScreen` → `settings.isArmed=true`). `App.tsx`'s `useBackgroundAlarmScheduler` calls `scheduleAlarmNotification()`, which calls `ClockGuardAlarm.schedule(h, m, days, title, body)`.
2. **Native schedule** (`ClockGuardAlarm.kt` from `withAlarmClock.js`). The schedule is saved in SharedPreferences `clockguard_alarm`. `AlarmManager.setAlarmClock()` is set for the next matching day.
3. **Fire.** `ClockGuardAlarmReceiver` sets a "pending ring" flag and posts a CATEGORY_ALARM notification with `setFullScreenIntent`. In `finally` it schedules the next repeat day.
4. **Launch.** The full-screen intent opens `MainActivity` with an extra. `AlarmLaunchHelper` (regex-injected into `onCreate`) sets `showWhenLocked`/`turnScreenOn`.
5. **JS takes over.** `useNativeAlarmLaunch` reads `consumePendingRing()` and calls `startPreview()`, so the status is `ringing`. It then **cancels the native notification**. `RingingScreen` plays the tone with `expo-audio` and pulses haptics.
6. **Snooze.** The correct PIN sets status `snoozed`. The countdown is a JS `setInterval`; when it reaches 0, status goes back to `ringing`.
7. **Disarm.** Correct barcode (after movement) calls `dismissWake()`: status `idle` and `isArmed=false`, so the native alarm is cancelled.
8. **Boot.** `ClockGuardBootReceiver` reschedules on `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`.

### Structural weaknesses (root causes of the current bugs)
- **Sound lives in the screen.** It only plays while the Activity is in the foreground. Power button, Back gesture or Home all silence it. *(User-confirmed on device, 2026-10-31.)*
- **Ring and snooze state are only React state.** If the process dies or is swiped away, the alarm is gone. The snooze timer dies with the process.
- **Native code is Kotlin in JS template strings,** wired by regex patching of `MainActivity.kt` / `MainApplication.kt`. A template change silently no-ops (this happened once, fixed in `da05c03`, *history*).
- **Two schedulers exist** (native and the expo-notifications fallback), and three notification paths with their own listeners in `App.tsx`.

## 5. Target architecture (planned, not yet implemented)
See [STATUS.md → Next steps](STATUS.md#prioritized-next-steps). In short: a local Expo module `modules/clockguard-alarm` owns scheduling, a **foreground ring service** (sound, vibration, wake lock, persistent full-screen notification), the persisted ring/snooze state, boot recovery and the lock-screen flags. JS only renders state and calls `arm / cancel / snooze / disarm`. The current engine stays in place until the new module compiles in CI (DECISIONS T-07).
