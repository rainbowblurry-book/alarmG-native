# Okay I'll do that and I see that the app has a problem that is it doesn't auto open and run when. The time comes this needs to be handled so it's like a native alarm and not clicking on notification to open the app and then disarm.

Yes, this can be fixed so it behaves like a real alarm. It needs native Android code, which is why it's been logged as the one permanent gap on issue \#1. `expo-notifications` can't do it because its JavaScript API doesn't expose Android's full-screen intent.[^3_1][^3_2]

## How real alarm apps do it

Google Clock and Alarmy use this chain:

1. **`AlarmManager.setAlarmClock()`** schedules the exact wake time. Android treats it as a real alarm clock, shows the alarm icon in the status bar, and lets it wake the phone from sleep.[^3_3]
2. **A native receiver fires at that time** and posts a high-priority alarm notification with `setFullScreenIntent()` pointing at your app.
3. **The app opens by itself** over the lock screen. Your existing `withLockScreenBypass` module handles the showWhenLocked/turnScreenOn part.[^3_4]

One Android rule to know: full-screen only takes over when the screen is off or locked. If you're actively using the phone, Android shows a big banner at the top instead. Google Clock works the same way, so that's normal, not a bug.

## The Android 14 catch

On Android 14 and newer, `USE_FULL_SCREEN_INTENT` became a special permission. Only calling and alarm apps get it by default, and the user can turn it off.[^3_5][^3_6]

- Your `app.json` already declares it, and sideloaded APKs usually get it enabled on install.[^3_6][^3_7]
- The app should still call `canUseFullScreenIntent()`. If that returns false, it should open the "Manage full screen intents" settings page so the user can turn it on.[^3_5]
- When you publish on Play, you'll have to declare ClockGuard as an alarm app in the Play Console.[^3_8]


## My plan (on a new branch `fullscreen-alarm`, main stays safe)

I'd write this as a native module added through a config plugin, the same pattern that already works for `withLockScreenBypass`:

- **`plugins/withAlarmClock.js`:** injects a Kotlin `AlarmClockModule` (schedule and cancel with `setAlarmClock`), an `AlarmReceiver` that posts the full-screen notification, a boot receiver that re-schedules the alarm after the phone restarts, and the manifest entries they need.
- **`src/native/alarmClock.ts`:** a small JavaScript wrapper with `scheduleAlarm`, `cancelAlarm`, `canUseFullScreen` and `openFullScreenSettings`.
- **`App.tsx`:** swaps the `expo-notifications` scheduling for the native module and starts ringing automatically when the app is opened by the alarm, not only when you tap the notification.
- **Settings screen:** a warning card if the full-screen permission is off, with a button that opens the right settings page.

The other option is the Notifee library (`fullScreenAction`), which needs less custom code. I'd avoid it because I can't confirm it works with your React Native 0.86 new-architecture setup, and it would add a native dependency you don't control. The custom module fits what you already have.[^3_9]

## Why it doesn't auto-open

Your alarm is a one-time scheduled notification from `expo-notifications`, set for the next matching day. That library has no way to add Android's full-screen launch, so the app can only open when you tap the notification. The native plan from before is the right fix.[^4_1]

## Bugs I found

1. **The alarm can get cancelled by itself.** `SettingsContext` sets `isArmed` back to `false` every time the app loads. Then `useBackgroundAlarmScheduler` in `App.tsx` sees `isArmed = false` and calls `cancelScheduledAlarm()`. So if you arm the alarm and Android kills the app overnight (Samsung does this a lot), the next launch deletes the scheduled alarm. The native version will save the armed state for real so this can't happen.[^4_3][^4_7]
2. **Repeat days only work if you open the app.** Only the next alarm gets scheduled. It fires once, and the following day's alarm is only set when the app runs again. The native receiver will schedule the next day itself, and also after a phone restart.[^4_1]
3. **There's a Dismiss button that skips the mission.** The notification has Dismiss and Snooze buttons. Tapping either one clears the notification without ringing or asking for the barcode. That lets a sleepy user skip the whole wake-up mission. I'll remove both buttons, since real alarm apps like Alarmy don't offer a free dismiss.[^4_7][^4_1]

# 1. useCurrentTimeWhenIdle overwrites the alarm time when native alarm auto-launches, before disarm — could point next-arm at the wrong time

File: App.tsx. When the native alarm fires and opens the app, wakeFlow.status flips to ringing via useNativeAlarmLaunch, but there's a window on cold start where wakeFlow.status is still 'idle' (default state) and settings.isArmed is still true — setToNow() runs on mount and on every AppState "active" event, and its only guard is isArmed || status !== 'idle'. On a cold start triggered by the alarm, React hasn't rendered the ringing state yet when the mount effect fires, so setToNow() can overwrite alarmHour/alarmMinute to the current time while the app is still armed and about to ring. This doesn't stop the current ring (native alarm already fired independently), but it silently corrupts what the wheels show and what gets rescheduled if the user re-arms right after — they'll see/re-arm the current time instead of their real wake time.
Fix: add a check for a pending ring (native consumePendingRing-style flag, or track justLaunchedFromAlarm similarly to AlarmLaunchHelper.applyIfAlarm) and skip setToNow() when the activity was launched by the alarm intent.

1. Wrong-PIN / wrong-barcode do not stop the alarm audio or haptics, but that's expected — however cruelty-mode nextSnoozeSeconds in RingingScreen reads wakeFlow.currentSnoozeDurationSeconds, not .snoozeCount, causing a possible off-by-one display vs. actual next duration
File: RingingScreen.tsx. Minor logic duplication risk: nextSnoozeSeconds is computed independently in the UI from the same formula as startSnooze in WakeFlowContext.tsx. If one changes and not the other (likely during future edits), the displayed "next snooze will be Xs" can lie to the user about the real cruelty-mode duration they're about to get. Not a bypass, but a trust/UX correctness bug adjacent to a punitive feature — worth locking down now while it's fresh in your head.
Fix: derive nextSnoozeSeconds from a single exported helper function (e.g. move the halving formula into WakeFlowContext.tsx and export it) instead of re-implementing it in RingingScreen.tsx.
2. ClockGuardAlarmReceiver.onReceive calls ClockGuardAlarmStore.load(context) and continues even if MainActivity is dead — but scheduleNext runs unconditionally after notifier.show, meaning a crash/exception in Notifier.show (e.g. SecurityException swallowed) still reschedules, but a crash before that line would skip rescheduling entirely and silently kill all future repeats
File: withAlarmClock.js, Kotlin ClockGuardAlarmReceiver. There's no try/catch around the receiver body. BroadcastReceiver.onReceive has a strict execution time limit (~10s on modern Android) and any uncaught exception here (e.g. NotificationManager in a bad state, OEM restriction) will crash silently in the background — the user won't see a stack trace, they'll just get no alarm and no next-day reschedule, which is the single worst failure mode for an alarm app.
Fix: wrap the receiver body in try/catch, and call ClockGuardAlarmScheduling.scheduleNext(context) in a finally block so a notification failure never cancels the next day's alarm.

Yes—this is **fixable**, and you’re right: pressing the power button should turn the screen off, not provide a free way to silence ClockGuard.

I checked `c0aa39d`: that commit changes only the developer “Exit Preview” handler, not power-button or audio behaviour. So it doesn’t establish that the power button is deliberately triggering snooze.[^37_1]

## What’s probably happening

There are two different possibilities:


| After pressing power | What that means |
| :-- | :-- |
| You unlock and see **“Snoozed” with a countdown** | The app actually entered snooze without the PIN—a state-handling bug. |
| You unlock and still see **“Alarm active”**, but sound stopped while locked | The alarm never snoozed; its audio stopped when the screen locked—a background-playback problem. |

The second explanation is plausible: Expo audio requires background-playback configuration to keep sound playing when the screen locks, and its documented `shouldPlayInBackground` default is `false`. Android sustained playback also needs the appropriate foreground-service setup.[^37_2]

## What the proper fix should achieve

For ClockGuard, the target behaviour should be:
      - Power button: screen turns off, **alarm continues sounding**.
      - Locking or backgrounding: does not change ringing into snoozed or dismissed.
      - Snooze: only after the correct PIN.
      - Disarm: only after the required movement and matching barcode.
      - Alarm audio remains independent of whether the ringing screen is visible.

A robust implementation would keep the alarm sound running through an Android foreground service rather than relying solely on the visible screen’s player. Importantly, we should avoid introducing ordinary media “pause” controls that become another way to bypass the mission. Android’s background-audio support uses foreground services, but the exact implementation needs checking against your installed Expo version before choosing the fix.[^37_2]

This fixes the normal screen-lock bypass; it cannot make the app immune to someone deliberately force-stopping it or turning the phone off.

**One quick check:** after pressing power and then unlocking, do you see **“Snoozed” plus a countdown**, or **“Alarm active” with the sound stopped**? That tells us which problem to address—no code or new build needed just to identify it.
